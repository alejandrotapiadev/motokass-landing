02

Flujo de compra

Lo que vive el cliente, de izquierda a derecha. Los colores indican quién hace cada paso: nuestra web Stripe confirmación.

Carrito/carrito · «Tramitar pedido». Si está activado, «Prefiero pedir por WhatsApp» como alternativa.
→
Datos y entrega/checkout · nombre, email, teléfono, envío o recogida, dirección, notas y aceptar condiciones.
→
Resumen realPrecios, stock, envío e IVA calculados por el servidor (/api/checkout/quote).
→
Crear pedido/api/checkout crea el pedido pending y reserva el stock.
→
Pago en StripePágina de Stripe. La tarjeta nunca pasa por nuestro servidor.
→
ConfirmaciónEl webhook marca el pedido como pagado y envía los emails. /checkout/success lo muestra.
Paga

Pedido confirmado

Stripe vuelve a /checkout/success. La página consulta el estado real y espera como máximo unos 40 s a que llegue el webhook («Estamos confirmando tu pago…»). Al confirmarse: se vacía el carrito, se registra purchase una sola vez y llegan los emails.

Cancela

Vuelve sin pagar

Stripe vuelve a /checkout/cancel. El servidor expira la sesión y devuelve el stock al momento. El carrito se conserva y el cliente puede volver al checkout.

Otros casos

Rechazo, abandono, pago lento

Tarjeta rechazada: el cliente puede reintentar en la misma página de Stripe. Si abandona, la sesión caduca a los 31 min y el stock vuelve. Los pagos asíncronos (p. ej. SEPA) mantienen la reserva hasta que Stripe confirma o rechaza.

03

Secuencia técnica

Frontend → API → Stripe → Webhook → Pedido → Stock. La llegada a /checkout/success no confirma nada: la única fuente de verdad del pago es el webhook.

04

Stock: reserva al iniciar el pago

El stock se descuenta cuando el cliente empieza a pagar, no cuando termina. Así nunca se cobra a dos personas la misma última unidad. Si el pago no se completa, las unidades vuelven al stock una sola vez.

Reservacreate_checkout_order() descuenta el stock con UPDATE … WHERE stock ≥ n, todo en una transacción. Si falta stock en cualquier línea, se revierte el pedido entero.
Ventana de pagoLa reserva dura 30 min (el mínimo de Stripe) y la sesión de Stripe caduca 1 min después.
PagadoEl webhook confirma el pago. El stock ya estaba descontado y no se vuelve a tocar.
O se liberaSi el cliente cancela, la sesión expira o el pago falla, el stock vuelve una sola vez (flag stock_reserved).

Concurrencia: dos clientes, una unidad

Cliente A

Reserva la unidad

UPDATE … SET stock = 0 WHERE stock ≥ 1 → 1 fila afectada. Continúa a Stripe.

PostgreSQLbloqueo de fila
stock = 1 → 0
Cliente B

No llega a pagar

La misma sentencia ya afecta a 0 filas → out_of_stock. Ve «La cantidad solicitada supera el stock disponible» antes de pagar.

Redes de seguridad

Evento

checkout.session.expired

Stripe avisa de que la sesión caducó → se libera el stock.

Oportunista

En cada checkout

release_expired_reservations() limpia las reservas vencidas antes de crear un pedido nuevo.

Cron diario

/api/cron/liberar-reservas

Cada día a las 04:00 UTC, con 10 min de margen, por si no llegó el webhook.

Botón «atrás»

Reintento del cliente

Si vuelve desde Stripe con el botón del navegador y reintenta, el pedido anterior se cancela primero (sessionStorage) para no bloquear su propio stock.

Cobro tardío

Pago tras liberar

Se intenta reservar de nuevo. Si ya no hay stock, el pedido queda requires_attention y la tienda recibe el email con «[REVISAR]».

Reembolsos

No reponen stock

Es intencionado: hay que revisar el producto devuelto antes de volver a venderlo.

Webhook de Stripe

POST /api/webhooks/stripe · lógica en src/lib/commerce/stripe-webhook.ts. Es la única fuente de verdad del estado de pago.

1 · FirmaSe verifica con STRIPE_WEBHOOK_SECRET sobre el cuerpo sin procesar. Si no es válida → 400.
→
2 · ¿Duplicado?Si stripe_webhook_events ya lo tiene como procesado → 200 duplicate.
→
3 · AplicarFunción SQL idempotente con bloqueo de fila.
→
4 · EmailsSe reclaman en la BD antes de enviarse: nunca se duplican.
→
5 · Responder200 si todo fue bien. 500 si algo falló, y Stripe reintenta con backoff hasta 3 días.

Eventos que hay que registrar en Stripe

EventoEfecto en el pedidoStockEmails

Si llega un evento con un order_id que no existe en esta base de datos (p. ej. de otro entorno), se responde 200 con unknown_order: reintentarlo no lo arreglaría. Los eventos de otros productos de Stripe se ignoran con 200.

08

Seguridad

Prioridad: seguridad > integridad de pedidos > integridad del stock > consistencia de pagos > UX.

Precios

El navegador no fija importes

Solo envía producto, variante y cantidad; cualquier otro campo se descarta. El servidor calcula precio, envío, IVA y total con Supabase. El precio se vuelve a verificar en la transacción (price_changed) y la sesión de Stripe se rechaza si su suma no coincide con el pedido.

Stock

Atómico y sin negativos

Descuento condicional con bloqueo de fila, orden fijo de bloqueos para evitar deadlocks, CHECK stock ≥ 0 y liberación idempotente.

Tarjetas

Nunca en nuestro servidor

Stripe Checkout alojado. No se guarda ni se registra en logs ningún dato de tarjeta.

Webhook

Firma + idempotencia

Firma verificada. Deduplicación en tres niveles: evento, transición de estado (bloqueo de fila) y email (reclamado en BD).

Base de datos

RLS sin políticas

anon/authenticated no pueden leer ni escribir pedidos, modificar precios o stock, ni ejecutar las funciones. Todo pasa por service_role desde el servidor.

Entrada

Validación con Zod

Esquemas compartidos cliente/servidor, cantidades de 1 a 10 por línea, máximo 50 líneas y límite de tamaño de la petición. Código postal validado para ES/PT.

CSRF y abuso

Origin + límite de peticiones

Como el proyecto tiene checkOrigin: false, las rutas POST comprueban el Origin. Límite de peticiones por IP en cada endpoint.

Acceso al pedido

Token de 256 bits

Success/cancel usan un token aleatorio. Solo se guarda su SHA-256 y se compara en tiempo constante. Páginas con no-store y no-referrer; el estado se consulta por POST para que el token no quede en logs.

Privacidad

XSS y logs

Datos del cliente escapados en los emails. Los logs solo contienen tipo e id del evento o número de pedido, nunca datos personales.

Tests automáticos (186 en verde)

  • Carrito: producto válido, cantidad válida e inválida, líneas duplicadas.
  • Checkout: precio manipulado, producto inexistente, desactivado o sin stock, cantidad superior al stock, país no admitido, Stripe caído (el stock vuelve), doble envío.
  • Pedidos: creación, foto fija del producto, IVA, número legible, transiciones inválidas, importes inmutables.
  • Webhook: firma válida, inválida y ausente, evento duplicado, pago completado, asíncrono fallido, expirado, reembolso, fallo de email con reintento, logs sin datos personales.
  • Stock: descuento correcto, webhook duplicado, concurrencia sobre la última unidad, cobro tardío, liberación única.
  • Seguridad: anon no puede marcar pedidos como pagados, modificar precios o stock, ni leer pedidos.
  • Interfaz: errores de formulario, bloqueo del doble clic, redirección a Stripe, errores del servidor comprensibles.

En los tests la pasarela de Stripe está simulada (las firmas de los webhooks sí son reales). La integración con la API real de Stripe hay que comprobarla con los pasos de arriba.
